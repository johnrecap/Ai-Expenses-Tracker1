## User Scenarios & Testing

### User Story 1 - Add Expense Quickly (Priority: P1)

As a user, I want a quick manual expense entry screen so I can see the primary add flow.

**Why this priority**: Quick mode is the safest primary add flow and validates amount entry, category selection, and form CTA behavior.

**Independent Test**: Open `/expenses/new/quick`, enter a mock amount, choose a category, and tap save with local feedback only.

**Acceptance Scenarios**:

1. **Given** quick add opens, **When** amount text is entered, **Then** the amount hero updates without overflow.
2. **Given** save is tapped, **When** no backend exists, **Then** the app shows local feedback or navigates back only.

---

### User Story 2 - Review AI Text And Receipt Modes (Priority: P2)

As a reviewer, I want AI text and receipt add modes to look complete while remaining offline.

**Why this priority**: These screens are high-risk because they visually suggest AI parsing, OCR, camera, and upload behavior.

**Independent Test**: Open text and receipt routes, trigger parse/upload controls, and confirm local mock state changes only.

**Acceptance Scenarios**:

1. **Given** AI text mode, **When** parse is tapped, **Then** a local mock suggestion appears without an API call.
2. **Given** receipt mode, **When** upload/camera is tapped, **Then** a mock parsed state appears without platform permissions.

---

### User Story 3 - Edit Existing Mock Expense (Priority: P2)

As a user, I want to open an existing expense for visual editing using mock data.

**Why this priority**: Edit flow validates route parameters, prefilled fields, and local-only form state.

**Independent Test**: Open `/expenses/:expenseId/edit` for known and unknown IDs.

**Acceptance Scenarios**:

1. **Given** a known mock expense ID, **When** edit opens, **Then** fields are prefilled from static mock data.
2. **Given** an unknown ID, **When** edit opens, **Then** the app shows not-found or safe fallback rather than crashing.

### Edge Cases

- Amount hero may overflow at 360px.
- Keyboard can hide submit CTA.
- AI text can grow past viewport.
- Receipt screen must not use camera/OCR/file picker.
- Edit form must not mutate global mock data permanently.

## Requirements

### Functional Requirements

- **FR-001**: `/expenses/new/quick` MUST render the quick add expense UI.
- **FR-002**: `/expenses/new/text` MUST render the AI text add UI with local mock parse behavior only.
- **FR-003**: `/expenses/new/receipt` MUST render the receipt add UI with local mock upload/parsed behavior only.
- **FR-004**: `/expenses/:expenseId/edit` MUST render an edit form from mock expense data or a safe fallback.
- **FR-005**: Add/edit screens MUST share form, segmented mode, amount, AI parse, and receipt upload components.
- **FR-006**: Save/parse/upload controls MUST NOT call external services or platform permissions.
- **FR-007**: Layouts MUST fit 360x800, 375x812, and 390x844 in LTR and RTL.
- **FR-008**: The feature MUST NOT add camera, OCR, microphone, file picker, AI API, backend, database, persistence, WebView, or HTML rendering.

### Key Entities

- **ExpenseDraft**: Local form state for amount, merchant, category, wallet, date, notes.
- **AddExpenseMode**: Quick, AI text, or receipt.
- **MockParsedExpense**: Local suggestion generated by toggling mock parse/upload state.

## Success Criteria

### Measurable Outcomes

- **SC-001**: All four add/edit screens render without overflow at required viewports.
- **SC-002**: Tests prove parse/upload/save actions change local UI only.
- **SC-003**: Known and unknown edit route IDs are handled without crash.
- **SC-004**: Forbidden dependency search has zero implementation hits for camera, OCR, speech, AI, backend, API, database, persistence, WebView, or HTML rendering.

## Assumptions

- Expense categories, wallets, and mock expenses are available from foundation/dashboard work.
- Save can show a snackbar or navigate back; it does not need to update global data.
